## TCP 和 UDP

### TCP 和 UDP 的区别

是传输层最常用的两种不同类型的协议，负责把应用层的数据报文传输给网络层。

- TCP 主要是为了在不可靠的 IP 网络之上，构建一条可靠、有序、流量可控、拥塞可控的数据管道
	- 是面向连接和字节流的，将数据看成无结构的字节流，在发送方和接收方建立一个连接，实现全双工一对一的通信。在这个通信过程中通过一系列控制例如超时重传，拥塞控制，流量控制等保证传输过程的可靠性。适合对于准确性要求高或者要求有连接并且对效率要求低的场景
		- 建立双方专属上下文，记录收发状态，保证通信隔离。
		- 滑动窗口管接收方本机，避免对方缓存爆掉；
		- 拥塞控制管中间网络，防止路由器堵包。
		- 具体
			- **面向连接、三次握手 / 四次挥手**
				痛点：无状态传输分不清新旧请求，无法协商初始序号、窗口大小。
				作用：建立双方专属上下文，记录收发状态，保证通信隔离。
			- **序列号 + ACK 确认应答**
						痛点：IP 包乱序、重复、丢失。
						作用：接收端排序、去重，发送方确认对方收到数据。
			- **超时重传 + 快速重传**
						痛点：链路丢包，数据发出去石沉大海。
						作用：自动补发丢失报文，上层无感知。
			- **滑动窗口（流量控制）**
						痛点：发送方疯狂发包，接收缓冲区撑爆丢包。
						作用：根据接收方剩余缓冲动态限制发送速度。
			- **拥塞控制（慢启动、拥塞避免、快恢复）**
						痛点：两端不限速猛发，路由器队列爆满，全网瘫痪。
						作用：探测网络承载能力，自动降速，防止全网拥堵。
			- **分段、重组、MSS 协商**
						痛点：链路 MTU 有限，大包会被 IP 分片，效率低。
						作用：TCP 提前拆分合适大小报文，优化传输效率。
			- **保活计时器、延迟 ACK、Nagle 算法**
						痛点：空连接长期占用资源、大量微小数据包浪费带宽。
						作用：优化资源占用、减少小包网络开销。
- UDP 是面向报文的，将应用层传来的报文加上 UDP 的首部后直接传输给网络层，没有任何控制和可靠性的保证措施，适合对于效率要求高且准确性要求低的场景

### 描述下 TCP3 次握手与 TCP4 次挥手，以及为什么要 3 次和 4 次

![sd](https://img1.sycdn.imooc.com//5d01c4d20001cc8e09600720.jpg)

#### 三次握手

三次握手主要是为了确认双方的收发功能都正常并且确认

![sa](https://pic1.zhimg.com/80/v2-576b043d12353928eea6e45373655668_720w.webp?source=1def8aca)

- 第一次握手，客户端向服务器发送一个 SYN 连接请求报文段，报文段的首部中 SYN 标志位置为 1，序号字段是一个任选的 随机数。它代表的是客户端数据的初始序号。
- 第二次握手，服务器端接收到客户端发送的 SYN 连接请求报文段后，服务器首先会为该连接分配 TCP 缓存和变量，然后向 客户端发送 SYN ACK 报文段，报文段的首部中 SYN 和 ACK 标志位都被置为 1，代表这是一个对 SYN 连接请求的确认， 同时序号字段是服务器端产生的一个任选的随机数，它代表的是服务器端数据的初始序号。确认号字段为客户端发送的序号 加一。
- 第三次握手，客户端接收到服务器的肯定应答后，它也会为这次 TCP 连接分配缓存和变量，同时向服务器端发送一个对服务器端的报文段的确认。第三次握手可以在报文段中携带数据。

#### 四次挥手

![](https://pica.zhimg.com/80/v2-c8b61ed2a249700583b11bc5d16c5711_720w.webp?source=1def8aca)

- 第一次挥手：客户端发送一个 FIN 报文，报文中会指定一个序列号。此时客户端处于 FIN_WAIT1 状态，停止发送数据，等待服务端的确认
- 第二次挥手：服务端收到 FIN 之后，会发送 ACK 报文，且把客户端的序列号值 +1 作为 ACK 报文的序列号值，表明已经收到客户端的报文了，此时服务端处于 CLOSE_WAIT 状态
- 第三次挥手：如果服务端也想断开连接了，和客户端的第一次挥手一样，发给 FIN 报文，且指定一个序列号。此时服务端处于 LAST_ACK 的状态
- 第四次挥手：客户端收到 FIN 之后，一样发送一个 ACK 报文作为应答，且把服务端的序列号值 +1 作为自己 ACK 报文的序列号值，此时客户端处于 TIME_WAIT 状态。需要过一阵子以确保服务端收到自己的 ACK 报文之后才会进入 CLOSED 状态，服务端收到 ACK 报文之后，就处于关闭连接了，处于 CLOSED 状态

##### 为什么需要 4 次挥手

服务端在收到客户端断开连接 Fin 报文后，并不会立即关闭连接，而是先发送一个 ACK 包先告诉客户端收到关闭连接的请求，只有当服务器的所有报文发送完毕之后，才发送 FIN 报文断开连接，因此需要四次挥手

##### 为什么客户端最后需要等待一会

确保最后一个 ACK 报文能够到达对方：在 TIME_WAIT 状态下，如果最后一次发送的 ACK 报文丢失，对方会因为没有收到确认而重新发送 FIN 报文。处于 TIME_WAIT 状态的一方能够重新发送 ACK。所以客户端最后会启动一个计时器，如果在时间内发现服务端重发了报文，需要重新发送报文，以此确保连接的可靠关闭。

- MSL 是 Maximum Segment Lifetime 的英文缩写，可译为 " 最长报文段寿命 "，它是任何报文在网络上存在的最长时间，超过这个时间报文将被丢弃。

TCP 的三次握手过程主要是为了确认服务器和客户端都具备发送和接收的能力。

1. 三次握手过程：
			1. 客户端首先发送一个握手连接请求，其同步位标志 SYN 为 1，并发送一个初始序列号，表示这是一个连接请求。
			2. 服务器接收到请求后，会对客户端表示确认，同时也发起握手请求。此时标志位 SYN 为 1，确认号 ACK 为客户端序列号加 1，同时发送服务器自己的序列号。
			3. 客户端接收到连接响应后，最后发送一个确认报文。此时大写 ACK 等于 1，小写 ack 等于服务器序列号加 1，并发送自己的序列号（即上一次发送的序列号加 1）。

接下来是四次挥手请求：

2. 四次挥手过程：
	1. 客户端向服务端发送结束连接的信息，将 FIN 标志位置为 1，并加上自己的序列号。
	2. 服务器接收到挥手请求后，先表达对客户端 FIN 请求的确认，即将大写 ACK 置为 1，小写 ack 等于前一个请求的序列号加 1，并带上自己的序列号。
	3. 由于服务器可能还有未发送完毕的报文，它需要等待片刻。待全部发送完成后，服务器再发送一个真实的连接关闭请求，即 FIN 标志位为 1，大写 ACK 为 1，小写 ack 仍然是对上一次请求的序列号加 1，并带上自己的序列号。
	4. 客户端接收到关闭请求后，向服务器发送最后的确认，即大写 ACK 等于自己的序列号，小写 ack 等于上一个序列号加 1。

## TCP 和 UDP 设计

TCP 之所以设计复杂，根源在于底层 IP 网络本身不可靠，存在丢包、乱序、拥塞、溢出等各类问题。为了让上层业务无需重复处理网络异常，标准化将排序、重传、流量控制、拥塞控制等全套容错逻辑内置在 TCP 中。

它包含大量状态机、计时器、动态窗口策略，存在多处性能取舍权衡，且业务开发日常不会直观接触底层传输过程，因此学习门槛高，属于偏底层网络专业知识；而 UDP 主动舍弃可靠性保障，仅保留基础端口复用能力，逻辑简单，但需要上层自行处理所有网络异常。
