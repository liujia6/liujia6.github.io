### Hook 的实现原理、为什么 Hook 不能写在 if / 循环里

核心：

Hook 依靠**调用顺序链表**存储每一次的 state、effect，每次渲染按顺序一一对应取值。

如果放在判断、循环中，渲染时 Hook 执行顺序错乱，数据匹配错位，直接报错。

## useMemo 和 useCallback 的使用场景

>useMemo 和 useCallback 不是性能银弹，它们本身也有成本
>只有当计算复杂度明显，或者引用稳定性会影响子组件更新时，才值得使用
>否则过度 memo 反而会增加 render 负担和代码复杂度

- useMemo
	- 缓存计算后的结果值（数字、数组、对象）。
	- 场景：大数据排序过滤等昂贵计算、传给子组件的字面量对象数组，避免重复计算、防止子组件无效刷新。
		- 计算很快（O (1)、简单运算）：不用 `useMemo`，缓存本身有开销，得不偿失；
		- 重开销计算（大数据 O (n)、排序、递归、复杂遍历）：用 `useMemo` 缓存结果，避免每次渲染重复算；
		- 额外场景：就算计算简单，但要把对象 / 数组字面量传给 `memo` 子组件，也要用 useMemo 稳住引用，防止子组件乱渲染。
- useCallback
	- 核心价值只有两点
		- 传给 `React.memo` 子组件：稳定引用，避免子组件无效重渲染；
		- 放进 `useEffect/useMemo` 依赖数组：防止副作用频繁执行。
	- 如果函数只在当前组件内部调用，不对外传递、不进依赖数组：
		- 每次渲染生成新函数完全没负面影响，缓存反而增加额外开销，属于多余优化。

## useReducer

- 理解 react 的 dispatch 和 reducer
	- 主要是为了达到数据变更的可控性
		- 通过拆分 dispatch 和 reduce 两层，明确数据只能怎么变更以及在哪里变更，达到数据的变更可控

我个人对 React useReducer 的理解是，React 在最初设计的时候，它的核心思想就是要解决复杂状态下的可预测性，不能随便变更。

所以 useReducer 是 React 对状态变更过程中的一个结构化工具。通过这套工具，它限制了状态变更必须由对应的事件触发，并且集中管理，这样会大大增强状态变更的可预测性，是符合它的核心需求的。

通过 useReducer 这套机制，一方面是对状态变更做了结构化的管理，统一放到一个函数里去做状态的变更逻辑处理；另一方面是通过事件的触发来表达状态变化的语义。

只不过在现代前端开发当中，实际上不需要做到这么强的约束，反而是一种多余的约束，通过简单的函数调用就可以做到。

但是我认为对于正常开发场景来说，可以通过封装 hooks，通过更加简单的函数去表达不同的变化语义，也可以通过一个更大的函数 map 去处理这种状态的集中变更，同样能够达到目的。相比 useReducer，这种方式减少了很多样板代码，逻辑更为清晰，心智负担也更小。

>useReducer 更适合状态机或复杂状态转换场景，它的设计更多是承载 Redux 的 reducer 思想，而不是推荐作为日常状态管理方式。

## UseLayoutEffect 和 UseEffect 的区别

Vue 默认渲染更新在绘制前完成（等同 useLayoutEffect），仅特殊场景用 nextTick；

React 默认副作用在绘制后执行（等同 nextTick），特殊防闪烁场景才用 useLayoutEffect。

绝大多数场景我们优先用 `useEffect`，像接口请求、异步数据获取都写在这里。这类操作耗时不可控，如果同步阻塞渲染会造成页面卡死，所以浏览器先渲染页面，再异步执行副作用，同时我们搭配 loading 状态，用户能预期页面变化，闪动也不影响体验。

而 `useLayoutEffect` 是 DOM 更新完成、页面绘制前同步执行，会短暂阻塞渲染，只适合快速的 DOM 操作：不管是调整元素宽高位置，还是修改文本、控制显隐，代码执行速度很快，短暂阻塞几乎无感知，但能避免浏览器先渲染错乱的临时界面，消除闪烁。典型场景就是弹窗居中定位。

总结：耗时不可控的异步数据操作用 `useEffect`；快速 DOM 修改、不想暴露中间错乱状态，就用 `useLayoutEffect`。

### 核心判断标准

useEffect 和 useLayoutEffect 的区别：

1. useEffect
这是我们大部分场景都会用来编写副作用的 Hook。它是在浏览器渲染之后执行的。像一些常见的数据接口请求以及数据更新的操作，都可以写在这个副作用函数里边。因为我们的核心是要保证页面首先渲染出来，然后再去做这些数据类的更新操作是没有问题的。

>这类操作优先等页面渲染完成再执行，用户能接受中间变化。

2. useLayoutEffect
当副作用里包含了一些对 DOM 本身的数据属性（包括布局大小之类的）更新时，就需要用到它。如果我们还是用 useEffect 的逻辑在之后执行，会导致页面在第一次渲染时，展示未更新前的布局状态，等到下一次渲染才会展示更新后正确的页面布局状态。这就会导致一个短暂的闪烁，影响用户的观感。所以使用 useLayoutEffect 在页面渲染前就计算完成并只做一次最终结果的渲染

简单区分：纯数据处理用 useEffect；修改 DOM 布局、避免页面闪烁的场景用 useLayoutEffect。

```js
useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setHeight(rect.height);
}, []);
useLayoutEffect(() => {
  ref.current.scrollTop = ref.current.scrollHeight;
}, []);
```

## useEffect

### 依赖数组 3 种规则

1. 不传依赖：每次组件更新都执行
2. 空数组 `[]`：仅组件挂载、卸载各执行一次
3. 填依赖项：依赖值发生变化时才重新执行

常见问题

- 漏写依赖：形成闭包陷阱，回调里拿到的是旧值，数据不同步

### 为什么 react 默认是渲染后副作用执行，而 vue 是渲染前阻塞

Vue 能默认把 DOM 相关逻辑放在绘制前，不只是为了降低上手成本，更是它整套响应式 + 微任务批量更新架构天然适配：它更新粒度细、没有并发渲染机制，统一在同步代码结束后一次性更新 DOM，少量阻塞不会影响交互。

但 React 完全没法照搬这套设计：

React 基于 Fiber 并发可中断渲染，必须保障主线程随时能响应用户输入。如果把所有副作用默认放到绘制前同步执行，会持续阻塞浏览器绘制，破坏时间切片、优先级调度的核心能力，复杂页面会严重卡顿。

同时绝大多数副作用不需要操作 DOM，同步前置只会白白拉长页面加载阻塞时间。

所以 React 只能做拆分设计：默认使用不阻塞渲染的 useEffect 处理绝大多数业务逻辑，仅布局修正这类特殊需求，才提供同步阻塞的 useLayoutEffect。

## 受控组件和非受控组件

- 受控
	- 业务需要主动修改组件显示值、同步状态、联动逻辑
- 非受控
	- 只让用户自由操作，代码只在最后读取结果，不干预过程、不改视图
- 整表要统一操作 → 全员受控
- 只有传文件 → 单独非受控
- 极简小表单 → 全员非受控

控制权放哪里，完全看场景：

1. 组件独立、无关联、无联动 → 控制权放组件内部（非受控）
	1. 逻辑内聚、代码干净、职责清晰、更好维护。
2. 组件之间有关联、有联动、有全局操作 → 控制权统一上交外层（受控）
	1. 方便统一管理、统一校验、重置、回填、联动、复用。

## useDeferredValue

`useDeferredValue` 是 React18 提供的并发 Hook，用于延迟非紧急的状态更新，让高优先级的用户交互（输入、点击）优先执行，不被大量渲染阻塞。

最常用场景：搜索框 + 长列表、大数据表格、频繁过滤筛选。

它和防抖最大区别是：防抖是固定延迟，而它是智能等待浏览器空闲，体验更优。

### useTransition vs useDeferredValue（超级好记）

- useTransition：包住 " 更新函数 "

```js

startTransition(() => {

setList(新数据)

})

```

- useDeferredValue：包住 " 要延迟的值 "

```js

const deferredInput = useDeferredValue(input)

```

效果一样，只是写法不同。

实战里：

1. 能直接控制 setState 更新逻辑 → 优先 useTransition
2. 没法直接改更新、仅消费数值 → 优先 useDeferredValue

- Fiber 只是具备优先级调度的底层能力，不会自动区分业务轻重；
- 你必须手动标记高低优先级，框架才知道该优先响应交互、暂缓繁重渲染。
