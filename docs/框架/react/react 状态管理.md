## 总结

- zustand
	- 符合大部分场景，全局状态管理，使用简单，符合 Hooks 思维，按需订阅
- jotai
	- 在状态依赖复杂（多种派生状态和 watch）时可用，可自动依赖管理
- mobx
	- 在状态依赖复杂的同时，还具有强领域性的对象
		- 比如编辑图，它有很强的实体性
- context
	- 多层级之间的数据共享，更加适合不变的配置数据
- redux
	- 没有使用过，其实 vue 的时候用的 vuex 时参考的 redux，那个时候的 vuex 就遭遇诟病，现在除非团队已经有完整 Redux 体系，否则不会优先选择。
- 父组件调度数据
	- 简单跨组件共享优先状态提升
- 组件内部状态
	- 优先 useState/useReducer，hooks

## context

更加适合多个组件需要用到的配置

例如全局的 theme，国际化配置

不适合高频更新，Context 更新会导致消费组件重新渲染。

## 跨组件复杂业务状态管理

大部分场景下，Zustand 都更适用于 React 的状态管理。它属于显式管理状态更新的一种模式，使用简单，符合 react 思想，并且是全局状态。在大部分场景下，全局状态的更新和管理用它就足够了。

因为大部分场景更多的是流程复杂，而不是状态之间的依赖关系复杂。但当真正碰到状态依赖关系非常复杂的情况，比如有非常多的派生关系或 watch 之类的逻辑，可能就需要用到像 MobX 和 Jotai 这样的自动依赖管理了。

这类似于 Vue 的思想，做响应式更新，因为在复杂场景下，人脑根本梳理不过来这些显式的依赖关系，需要自动化处理。

Jotai 和 MobX 的区别主要在于：

1. Jotai
	1. 适用于大部分的业务场景，它的特点是更加原子化。
2. MobX
	1. 适用于领域化特别强的业务。比如编辑图，它有很强的实体性，我们的实体上有很多对象属性（例如节点和边都有各自的大量属性），这种场景就适合用 MobX。

这个项目的公共状态更偏 " 应用运行时状态 + action + 副作用协调 "，zustand 的 store/action 模型更贴近；jotai 更适合很多细粒度 atom、派生状态、局部组合状态

## redux

Redux 的设计思想很简单，就两句话。

>（1）Web 应用是一个状态机，视图与状态是一一对应的。
>
>（2）所有的状态，保存在一个对象里面。

Store 收到 Action 以后，必须给出一个新的 State，这样 View 才会发生变化。这种 State 的计算过程就叫做 Reducer。

其实这玩意就是一个强制约束，reducer 用一行代码解释就是

>(state, action) => state
