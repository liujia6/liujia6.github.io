## 总结

- fiber 架构
	- 痛点
		- React 早期的 Virtual DOM Diff 采用递归遍历整棵树的方式执行，任务一旦开始就无法中断。当组件树较大时，可能长时间占用主线程。
	- 解决
		- 为了解决这个问题，React16 引入了 Fiber 架构。Fiber 可以理解为 Virtual DOM 的增强版节点，在原有 UI 描述信息的基础上增加了调度、优先级、副作用等运行时信息。同时将原本依赖递归调用栈的树遍历改造成基于 child、sibling、return 指针的可遍历结构，使 React 能够把渲染任务拆分成多个小任务执行，从而实现可中断和可恢复的调度能力。
- setState 更新过程
	- 当 setState 执行后，React 会记录这次状态变化，然后交给调度系统处理。
	- React 会批量收集同一轮所有状态修改，统一开启一次更新流程；
	- 调度系统会根据更新的优先级决定什么时候执行更新，例如用户交互类更新优先级较高，需要尽快响应。
		- 也可中断让出给优先级更高的
	- 确定执行更新后，会进入 Render 阶段：
		1. fiber 最小单位的调度执行
			- 以 Fiber 为最小单位
			- 每执行一个 Fiber：
				- 检查时间片
				- 不够就暂停
			- 可以被更高优先级任务打断
		2. React 基于 Fiber 架构重新计算组件状态和 UI，构建新的 Fiber Tree。
		3. 通过 Diff 算法比较新旧 Fiber Tree，找出变化部分并标记需要执行的更新操作
	1. 进入 Commit 阶段：
		1. React 根据之前标记的更新操作，一次性同步修改真实 DOM。
	2. 执行 useLayoutEffect。
	- 浏览器页面绘制。
	- React 异步执行 useEffect。

## 三、把「Fiber + Scheduler」压缩成一句话

你在面试中可以这样说（非常稳）：

>React 在状态更新后不会立刻渲染，而是先将更新任务交给 Scheduler，根据优先级调度执行，Render 阶段以 Fiber 为最小单位进行可中断的计算，最终在 Commit 阶段一次性提交变更； Vue 则通过响应式系统精确追踪依赖，在状态变化时同步批量执行更新，追求的是更新最少而非可中断。

---

React 调度的目标是：

>永远不要让主线程 >300ms 不可响应 即使大任务还没完成，关键事情（用户输入、动画、交互）仍能及时响应。

完整逻辑

- React 通过调度系统避免主线程被长时间占用，保证 UI 在复杂更新下依然可响应；但 Fiber 本身并不保证性能优化，流畅性仍取决于开发者如何控制更新范围和计算成本。
- Vue 的更新以 " 尽快完成 " 为目标，而 React Fiber 以 " 可中断和响应性 " 为第一目标；在高并发 UI 和复杂交互下，React 能保证应用不失去响应，但是否流畅仍依赖业务优化。
- vue 是低级开发者，收集好任务后，一个个尽快完成任务，除此以外啥都不管，领导来了还没做完也不理睬
- react 是高级开发者，做了时间和任务管理，对任务拆分和计划，定时了解领导需求和汇报，做好任务的优先级管理和安排

## 四、什么时候 React 的性能优势才会显现？

你可以主动补一句（加分）：

- React Fiber 的调度优势在大计算 + 高频交互并存时才会明显，比如大列表搜索、复杂表单、拖拽编辑器这类场景
- 如果只是普通 CRUD 页面，其实 Vue 的同步更新模型更简单直接，体验差异并不明显
- 低端设备

## 类似 requestIdleCallback 的调度机制？不是用的 requestIdleCallback 吗

你抓住了非常核心的一个重点。答案是：确实没有用原生的 requestIdleCallback (rIC)。

React 官方团队在早期尝试过它，但很快就放弃了。现在 React 内部负责调度的核心模块叫 Scheduler（调度器），它是通过 MessageChannel（宏任务）配合 requestAnimationFrame（在某些老版本中）或纯时间切片自行模拟实现的。

放弃原生 requestIdleCallback 的原因非常现实，主要有以下三个致命痛点：

### 1. 致命伤：刷新率低，被浏览器限制在 20Hz

这是最核心的原因。 原生的 requestIdleCallback 被浏览器贴心（但保守）地设定了一个保底限制：它的触发频率最高只有每秒 20 次（也就是大约 50ms 触发一次）。

- 浏览器的逻辑： 既然是 " 空闲 " 才执行的任务，那我就不着急，每 50ms 看一眼就行了。
- React 的灾难： 现代显示器很多都是 60Hz、120Hz 甚至 144Hz。如果 React 的更新调度被死死卡在 20Hz，哪怕用户电脑性能再好、浏览器再空闲，React 一秒内也只能更新 20 次，这会导致页面看起来极度不流畅，人为制造卡顿。

### 2. 兼容性极其惨烈（尤其是 Safari）

在 React 16/17 开发的那几年，Safari 浏览器（包括 iOS 微信内置浏览器等）完全不支持 requestIdleCallback。

对于一个全球通用的顶尖框架来说，不能在 iPhone 和 Mac 默认浏览器上运行是绝对无法接受的。虽然可以通过 Polyfill（垫片）来解决，但既然都要自己写 Polyfill，React 团队索性自己写一套更完美的调度引擎。

### 3. 无法控制优先级与可控性

原生的 requestIdleCallback 是由浏览器完全主导的。浏览器说现在有空，它才执行；浏览器说没空，它就死等。

React 的复杂应用中，有些任务虽然是异步的，但有明确的过期时间（Timeout）。比如用户输入虽然高优先，但某个普通的点击事件更新也不能等超过 500ms，否则用户会觉得网站死掉了。 原生 rIC 的超时机制（timeout 参数）控制粒度太粗，无法满足 React 内部对 Immediate、UserBlocking、Normal、Low 等多级优先级的精确计算和插队逻辑。

### React 是如何自己模拟实现的？

既然原生的不好用，React 团队自己基于浏览器的 事件循环（Event Loop） 机制，用 MessageChannel 搓出了一个高频、高性能的 " 空闲调度器 "。

#### 为什么选择 MessageChannel？

React 需要一种能让出主线程、但能以最快速度被重新唤醒的宏任务（Macrotask）。

- setTimeout(fn, 0)：看起来可行，但浏览器为了防止死循环，嵌套 5 层以上后会有 4ms 的最小延迟，浪费性能。
- Promise.then（微任务）：微任务在当前渲染帧结束前会一口气全部执行完，根本无法实现 " 把执行权还给浏览器去画页面 " 的目的。
- MessageChannel（宏任务）：它的执行时机紧随在浏览器渲染/事件处理之后，而且没有 4ms 的人为延迟。

#### 它的工作原理（简易版流程）

React 的 Scheduler 内部是这样和浏览器 " 极限拉扯 " 的：

1. 计算时间预算：React 设定一帧的干活时间大概是 5ms。
2. 开始干活：记录当前时间戳 startTime。
3. 循环检查：每处理完一个 Fiber 节点，React 都会用 performance.now() - startTime。如果超过了 5ms，说明这帧的指标用完了。
4. 让出主线程：React 停止遍历，然后通过 port.postMessage() 发送一个消息。
5. 浏览器喘息：主线程空出来了，浏览器可以高优先地去处理用户输入、执行 Layout 和 Paint。
6. 瞬间唤醒：一旦浏览器把这一帧的紧急活干完，宏任务队列里的 MessageChannel 回调立刻被触发，React 顺着刚才停下的 Fiber 指针继续往下干。

>面试得分点总结： " 面试官经常会误以为 Fiber 用的是 requestIdleCallback。但实际上，因为原生 rIC 存在 Safari 兼容性差、最高只有 20Hz 刷新率 以及 无法精准控制优先级 的缺点，React 团队在底层自己实现了一个 Scheduler 模块。 它是基于 MessageChannel 宏任务和纯时间切片（默认 5ms）来模拟的，从而保证了在各种浏览器下都能以最高效、最流畅的频率进行任务暂停与恢复。"

## 一、先回答你的核心疑问：面试官问「React 渲染流程」要不要全说完？

分两种层次，不用一股脑全部抛出：

1. **基础回答（初级/普通面试）**：只讲主线流程，Fiber 时间切片、优先级中断简单带过，讲清 `setState → Render → Commit → 两个Hook时序` 即可；
2. **深度回答（中高级/深挖底层）**：再展开调度系统、并发更新、可中断、Diff 细节；
标准策略：**先讲最简主线，面试官追问再逐层补充细节**，不要一次性堆砌全部知识点，逻辑清晰不杂乱。

## 二、精简版完整渲染流程（背诵主线版，无冗余）

调用 `setState` 触发更新完整链路：

1. 标记状态变更，交给调度系统，批量收集本轮所有状态更新；
2. 调度系统区分更新优先级，高优任务优先执行，协调阶段可中断、让出主线程；
3. Render 阶段（协调，可中断）
   - 以 Fiber 为单元分片执行，超时则暂停；
   - 生成新 Fiber 树，Diff 对比新旧树，记录 DOM 变更标记；
4. Commit 阶段（同步、不可中断）
   - 根据标记批量操作真实 DOM；
   - DOM 更新完成，同步执行 `useLayoutEffect`；
5. 浏览器布局、绘制页面；
6. 页面渲染完成后，微任务异步执行 `useEffect`。

## 三、拆分成递进式子问题回答结构（面试分步口述，层层递进）

### 子问题 1：setState 调用后第一步发生什么？（调度 + 批量更新）

执行 setState 不会立刻更新视图：

1. 先标记组件状态发生变化；
2. 同一同步上下文多次 setState 会批量合并，只触发一轮更新；
3. 全部更新交给调度系统，区分优先级（点击/输入等高优优先）。

### 子问题 2：什么是并发协调、Fiber 时间切片？（Render 阶段核心）

调度系统开始执行更新，进入 Render 协调阶段：

1. 采用 Fiber 架构，组件拆分为最小 Fiber 节点；
2. 使用 5ms 时间切片，单轮执行超时就暂停，把主线程还给浏览器；
3. 高优先级任务到来时，可打断当前渲染，优先处理交互；
4. 遍历生成全新 Fiber 树，通过 Diff 对比新旧节点，记录所有 DOM 修改操作。

### 子问题 3：Commit 阶段做什么？顺序是什么？

Render 阶段完成后进入 Commit，全程同步、无法中断：

1. 根据 Diff 记录的补丁，一次性批量修改真实 DOM；
2. DOM 修改完毕、页面还没绘制，同步执行 `useLayoutEffect`。

### 子问题 4：useLayoutEffect 和 useEffect 的执行顺序、时机差异？

1. Commit 结束后先交给浏览器布局、绘制屏幕，用户能看到页面；
2. 绘制完成后，将 useEffect 放入微任务队列异步执行；
3. 区别总结：useLayoutEffect 绘制前同步执行，useEffect 绘制后异步执行。

### 子问题 5：串联完整闭环总结（收尾一句话）

整体流程：状态更新入调度 → 分片可中断 Render 生成补丁 → 同步 Commit 修改 DOM+ 执行 useLayoutEffect → 浏览器绘制 → 异步执行 useEffect。
