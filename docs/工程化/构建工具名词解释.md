问题

- Vite 为什么比 Webpack 快？两层架构（dev ESM + prod Rollup）完整口述；
- Vite 配置、插件机制、环境变量、legacy 兼容旧浏览器；
- Vite 和 Webpack 工作流程核心区别。
- 公司老 Webpack 项目构建太慢，怎么优化？（答案：优先迁移 Rspack，不用重写配置）
- Webpack 迁移 Rspack 成本？兼容性？
- Vite 大型项目体积膨胀、打包慢怎么优化（Rolldown 升级、分包策略）
答案

- 构建工具类型
	- 打包器：管依赖分析、合并代码、资源处理、分包、摇树（esbuild/Webpack/Rollup）
	- 转译器：只管语法翻译（SWC/Babel）
- 为什么用 rust
	- JS 是单线程，构建 CPU 密集型任务（AST 解析、代码压缩、依赖遍历）天生性能上限低；
	- Rust 无 GC、多线程、内存开销小，CPU 密集场景构建速度提升几倍到十几倍，解决大型工程构建卡顿痛点。
- 有哪些构建工具可选
	- webpack
		- **先全量打包再启动服务**，递归构建完整依赖图，项目越大启动越慢；HMR 需要重新遍历依赖重构建；JS 实现，性能上限低；
	- vite
		- 提高开发环境构建使用性能，以及 API 使用便捷度，（vite8）统一环境引擎，同时提高性能和一致性
		- 开发环境体验性能优化
			- 浏览器原生 ESM 按需加载，自己写的业务代码：懒加载请求处理
			- 预构建第三方依赖 ESM 包缓存
		- 配置体验好，开箱即用
			- **不存在 Loader 概念是最大区别**
				- Webpack 分 Loader（单文件转换）、Plugin（全局流程）两套体系；Vite 统一只用插件，靠 transform 钩子实现所有文件转换逻辑。
		- vite7 及以前 ：**esbuild + Rollup**
		- vite8：统一为单一引擎 Rolldown
			- 内部配套：**Oxc 做代码解析 / 转译、Lightning CSS 处理样式**，不再依赖 esbuild 做依赖预构建与转译 Vite。
			- 多线程并行处理，模块解析、转译、压缩全面提速。
		- 适合
			- 全新 Vue/React 项目，追求极致开发体验、开箱即用；中小型项目首选。
	- Rspack
		- 字节出品，Rust 重写的构建工具，**API 99% 兼容 Webpack**；
		- **Rust 内核 + 内置 SWC/LightningCSS**，全链路性能拉满；
		- 适合
			- 原有 Webpack 复杂项目，只想提速、不想重构配置；企业级大型后台系统；
		- 具体
			- SWC
				- SWC (Speedy Web Compiler) 是一个基于 **Rust** 的超快速 **TypeScript / JavaScript** 编译器。它不仅仅是一个编译器，更像是一个可扩展的平台，可以用于编译、压缩、打包（实验性）、代码检查等。
				- SWC 存量项目极多，Webpack/Rspack 老项目替换 babel-loader 首选 SWC，改动极小；
				- **对标 babel**
			- Lightning CSS
				- 由 **Parcel 打包器团队** 用 **Rust 语言** 开发的**极速一站式 CSS 处理工具**，集**解析器、转换器、打包器、压缩器**于一体，对标并大幅替代 PostCSS 生态，Vite、Parcel 等主流构建工具已内置集成。
					Lightning CSS 是标准 CSS 的一些处理构建工具。 如果要使用 SCSS，同样是不冲突的，只需要在构建工具上前置处理就行了，是吧？
			- esbuild
				- **Go 语言编写的底层极速打包 / 转译内核工具**，定位：通用构建引擎、底层打包器。
					- 内置全套能力
						原生支持 TS/TSX、JSX、CSS、ESM/CJS 互相转换、Tree-Shaking、代码压缩、SourceMap、代码分割、监听模式、静态服务。
			- tsup
				- 专门打包 JS/TS 组件库、工具库，底层基于 esbuild，不用复杂配置，只输出 CommonJS + ESM 双格式，不适合业务应用打包。
			- Oxc = 一整套完整 Rust 前端工具套件（解析 + 转译 + 压缩 + Lint + 格式化 + 模块解析一体化）
				- **性能天花板**：Oxc 在解析、转换、内存占用上**全面超越 SWC**，且差距随优化持续扩大
				- Oxc 转换产物**干净、无冗余**，严格遵循标准 ESM，和 Vite「现代 ESM 优先」理念一致；同时支持**完整 TS/JSX 转换、精确类型擦除、稳定 HMR**，满足生产级要求 Oxc。
				- **Oxc + Rolldown**：**共享解析器与 AST**，打包时可并行处理类型检查、dts 生成、代码压缩，**一次解析、多阶段复用**，性能最大化。
			- Rollup
				- Rollup 从诞生起就**以 ESM 静态模块为核心**，设计理念和 Vite 完全对齐；
				- 它的模块解析、依赖分析、Tree-Shaking 全部基于 ESM 静态语法，不依赖运行时模拟模块系统。
				- Webpack 最初为 CommonJS 设计，ESM 是后续兼容能力，内部存在大量模块运行时、包裹代码，和 Vite「现代 ESM 极简产物」理念相悖。
				- **架构最优解**：Rollup 插件体系可直接复用，大幅降低 Vite 开发、生态、维护成本；
				- **产物可靠**：业界公认的优质打包产物、强 Tree-Shaking，满足应用 + 类库生产需求；
				- **职责解耦**：纯打包内核，和 Vite 的 Dev Server、HMR 分层清晰，架构优雅；
	- Turbopack：`Next.js` 专属，不能独立使用，超大 React 项目 HMR 极强
	- esbuild：只做转译内核，Vite 预构建依赖依赖它，不做完整应用打包；
	- Bun：Zig 编写，同时替代 Node + 打包 + 脚本运行，一体化工具链。

## 🔹 基础精简版（日常面试、一面快速作答，推荐）

Vite 和 Webpack 核心差异是**运行理念与速度**：

1. **开发环境**

	Vite 基于**浏览器原生 ESM**，不做全量打包，采用按需懒加载，仅对当前请求的模块做即时转译，彻底解决 Webpack 冷启动慢、模块全打包的问题，启动和 HMR 速度优势明显。

	Vite7 之前开发环境用 esbuild 做单文件转译，生产环境用 Rollup 打包。

2. **生产环境**

	官方基于 Rust 实现了 **Rolldown**（Rollup 重构版），既保留 Rollup 优秀的 Tree-Shaking、高质量产物、完整插件生态，又利用 Rust 大幅提升构建速度；同时统一开发、生产双引擎，解决了以往双工具行为不一致的问题。

3. **存量 Webpack 项目迁移**

	如果是传统 Webpack 老项目，首选 **Rspack**。它高度兼容 Webpack API 与配置，几乎可以无缝替换；底层基于 Rust 实现，搭配 SWC、Lightning CSS 分别处理 JS/TS、CSS，全方位提升编译与打包速度。

## 🔹 完整版（二面 / 深挖架构，补充原理，显得更专业）

Webpack 是**先打包、再运行**的传统思路，而 Vite 依托现代浏览器 ESM 能力，架构完全不同：

1. **开发阶段**

	Webpack 启动时会把所有模块打包成产物再提供给浏览器，项目越大冷启动越慢。

	Vite 不走全量打包流程，利用浏览器原生 ESM 按需加载，浏览器请求哪个模块，Vite 就用 esbuild（旧版）/Rolldown（新版）实时转译对应模块，启动速度、热更新速度远优于 Webpack。

2. **生产阶段**

	早期 Vite 生产构建使用 Rollup，它对 ESM 支持好、Tree-Shaking 精准、产物干净，但 JS 实现存在性能瓶颈。

	后续团队用 Rust 重写出 **Rolldown**，**100% 兼容 Rollup 插件与 API**，继承其打包优势，同时借助 Rust 多线程能力大幅提速；最终实现「开发、生产使用同一套内核」，消除环境差异 Bug。

3. **Webpack 存量项目方案**

	Rspack 定位是**Webpack 高性能替代品**，做到 99% 兼容 Webpack 配置、Loader、Plugin 生态，老项目基本零改动迁移。

	底层全栈 Rust 化，搭配 SWC 处理脚本转译压缩、Lightning CSS 处理样式，相比原生 Webpack 打包、编译速度提升数倍，是大型存量项目的最优解。

## 三、高频追问预判 + 标准答语（必背，面试官大概率接着问）

### 追问 1：为什么 Vite 开发用 ESM，生产还要打包？

答：

浏览器原生 ESM 适合开发调试，但生产环境存在**网络请求多、模块冗余、无代码分割 / 压缩、旧浏览器兼容**等问题，所以生产依然需要打包、合并、压缩、Tree-Shaking，来优化加载性能与兼容性。

### 追问 2：Vite 为什么早期 dev 用 esbuild、build 用 Rollup？

答：

- esbuild 速度极快，适合开发环境**单文件即时转译**；
- Rollup 专注 ESM 打包，Tree-Shaking、产物优化、Chunk 拆分能力更强，更适合生产构建；
- 缺点是双引擎导致**开发与生产行为不一致**，这也是后来开发 Rolldown 的核心原因。

### 追问 3：Rolldown 和原来的 Rollup 区别？

答：

Rolldown 是 Rust 重写的 Rollup，**完全兼容原有 API 和插件**；核心提升三点：

1. 性能大幅提升，解决 JS 版 Rollup 构建慢的问题；
2. 统一开发、生产构建内核，消除环境差异；
3. 增强代码分割、缓存、模块联邦等现代应用打包能力。

### 追问 4：Rspack 为什么选 SWC 而不是 Oxc？

答：

1. 时间窗口：Rspack 立项时 Oxc 尚未成熟，SWC 是当时主流成熟的 Rust 转译器；
2. 生态兼容：Rspack 主打 Webpack 无缝迁移，SWC 在 Webpack 生态中已有大量 Loader / 插件，Oxc 配置、行为不兼容；
3. 团队生态：Rspack 属于字节 Rstack 工具链，和 SWC 深度绑定，而 Oxc 是 Vite 团队自研体系。

### 追问 5：Vite 现在为什么转向 Oxc？

答：

Oxc 同团队自研，共享 AST 架构，解析、转译、压缩、Lint 一体化，减少重复解析开销，性能比 SWC 更强；同时和 Rolldown 深度集成，打造完整统一的下一代前端 Rust 工具链。
